# 从代码重建文档：说明与规范

Agent 在**提示用户是否重建**或**执行重建**前阅读本文件。

## 向用户说明时用的白话（可略作调整，须保留要点）

> 当前仓库里已有代码，但 intent / spec 里几乎还没有业务文档。  
> 可以选择进入「从代码重建文档」：我会阅读现有代码与 README 等线索，在对话里生成一批**带「推测」标记的草稿**（候选意图、行为规格、可能的架构决策）。  
>  
> **这些草稿不等于已确认的真相。** 代码能反映「现在怎么做」，很难可靠还原「为什么做、明确不做、曾否决的方案」。  
> **在你逐项确认之前，我不会把它们写成正式的 intent / spec / ADR。**  
> 你可以只重建某个模块，也可以现在说「不」。默认建议先不重建，需要时再说。

说明之后再询问是否进行；用户未明确同意则**不**开始重建。

## 触发条件（初始化末尾）

须**同时**满足才提示：

1. 仓库有实质代码（见 SKILL.md 启发式）
2. intent 与 spec 目录都几乎为空（仅索引 / 模板 / `.gitkeep`）

不提示：空仓、已有业务文档、用户只要初始化、冲突未解决。

用户也可在任意时刻显式要求「从代码重建文档」。

## 执行步骤

1. **分批范围：** 先列出候选模块/功能面清单，请用户选择本轮范围；禁止对巨型仓库一次倾倒全量。
2. **草稿载体（默认）：** 只在对话中展示；确认前不写正式文档路径。
3. **临时落盘（仅用户明确要求）：** 可写入 `docs/_drafts/`，并提示是否加入 `.gitignore`；确认后迁入正式路径并删除对应草稿。
4. **标记：** 凡未确认内容必须带推测标记（见下）。
5. **确认后落盘：** 去掉推测标记与「未确认」字样 → 写入对应 intent/spec/adr → 更新索引表。
6. **intent 特别克制：** 只写可观察线索 + 明确标出不确定项；禁止写成 Confirmed intent，除非用户明确 yes。

## 推测标记格式

文首：

```markdown
> 状态：推测草稿（未确认）  
> 来源：根据代码 / README 推断，可能不完整或有误  
> 请审阅后回复确认、修改或放弃
```

段落内不确定处使用：`（推测）` 或 `（不确定：…）`。

## 各类型重建侧重点

| 类型 | 适合从代码推断 | 必须标不确定 / 不宜武断 |
|------|----------------|-------------------------|
| spec | 路由、界面流程、校验、权限、错误提示等可观察行为 | 未实现的产品承诺 |
| adr | 已选用的框架、存储、部署形态、关键模式 | 「曾考虑但否决」的方案与完整权衡 |
| intent | 从 README/命名/主流程猜的 Outcome 线索 | Why now、Success、Out of scope——优先留空请用户补 |

## 禁止

- 未确认就写入正式 intent/spec/adr 并当作事实
- 为「显得完整」编造 Out of scope / Why now
- 覆盖已有正式文档
- 一次重建倾倒整个大型单体的全部模块
