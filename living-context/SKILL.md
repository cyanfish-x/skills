# Living Context

保存未来难以可靠重建、仍会影响判断的知识，让 Agent 理解证据、理由与真实约束，再独立判断。以更少的重复调查和错误复用衡量价值，文档数量和篇幅不是目标。

## 选择本次动作

- 开发任务：开始时检索相关知识；过程中识别冲突或昂贵发现；结束时只维护本次触及的知识。无需每次执行完整生命周期。
- 沉淀发现：用户主动提出时，在授权范围内核验并保存；Agent 自主发现时，按下文提出具体建议，确认后保存。需要表达示例时读取 [记录与路由](references/records.md)。
- 评估已有知识、建立入口、合并或清理知识：读取 [整理与重建](references/maintenance.md)。已有知识时，同时判断组织方式是否需要重建；有实际收益就主动提出具体方案，取得用户授权后迁移。

本文件是 skill 的执行入口。`design.md` 和 `living-context-v2.md` 是设计背景，仅在讨论设计本身时读取，不作为额外执行规则加载。本 skill 在被调用时执行工作，不提供后台巡检或每轮必然触发的保证。

## 开始：找到最小充分上下文

1. 从当前请求提取模块、行为、接口、依赖版本，以及用户限定的读取范围。优先读用户指向的材料和项目已有相关入口，例如 `docs/index.md`；没有入口时，在允许范围内按任务关键词搜索文件名或正文，不全量阅读文档。
2. 沿任务对应的链接读相关章节：行为看 Spec，目的看 Intent，职责和生命周期看 Architecture，选择理由看 Decisions，陷阱看 Engineering，外部证据看 Research。这些是语义用途，不是必须存在的目录。
3. 对会改变当前决定的关键结论，比较适用模块、版本、环境与当前任务。前提已变或证据不足时，做与风险相称的局部复核。未复核的旧记录只作为有边界的线索，不表述为本次已验证。
4. 当前任务的行为、真实约束、职责边界和关键风险已明确，且没有影响决定的未解冲突时，停止扩展阅读。新依赖或新证据出现后再展开。没搜到记录不代表没有约束，继续必要的需求和实现调查。

知识检索不扩大用户的任务范围，也不自动授权修改全库文档、个人记忆或宿主配置。

## 发现：用户提出与 Agent 自主识别

**用户主动提出**：例如“沉淀这次排障经验”“记录这个决策”。将其作为对应范围的沉淀授权，核验、提炼并保存，不再为同一动作重复确认。用户只是询问是否值得记录时，先给出判断与建议。

**Agent 自主发现**：在当前工作中遇到以下信号时，将其作为候选知识，而不是直接写入长期文档：

- 多轮排查确认了难以从代码表面恢复的根因。
- 实验推翻已有假设，或证明旧技术限制已经失效。
- 明确了非显然的真实约束、所有权或生命周期关系。
- 某个方案被放弃的理由，仍会影响未来选型。
- 重复调查同一问题，发现知识缺失或已有记录难以找到。

信号只触发价值判断，不意味着必须沉淀。检查现有相关记录，区分新增知识、应修订的旧结论和仅需改善的路由；容易重建、已经充分覆盖或不再相关的信息无需建议。重要但未确认的线索可以成为候选，必须保留假设性质与最小复核动作。

发现时在当前工作上下文中保留必要的结论、证据位置、适用条件和未知项，不为候选自动创建长期文档或另设知识收集系统。通常在任务结束时集中提出有价值的建议；只有证据即将丢失或影响当前决定时才提前说明，避免逐条打断用户。

建议应直接给出拟沉淀的内容、依据与边界、未来用途，以及具体目标文件或章节和新增／修订动作，再请求确认；不要只问“要不要记录”。目标需要新建时明确说明。确认前继续完成不依赖沉淀授权的任务工作，不把待确认建议报告为已保存。

用户确认后落盘；已有明确覆盖本次内容的持续维护或文档同步授权时，直接维护并报告，无需逐条确认。单纯加载 skill 或授权功能实现不等于持续沉淀授权，也不要给原本已授权的文档维护增加审批。用户拒绝或暂缓后，没有新证据或重新提出的需求就不重复建议。

## 判断：依据与约束力分开

对影响决定的陈述，分别判断：

- **依据是什么**：事实、特定环境下的观察，还是尚未检验的推测？来源能否支持它声称的范围？
- **对项目有何作用**：要求、已采纳决策，还是建议？若声称必须遵守，确认来源与适用范围是什么？

外部源码事实不自动成为项目要求；写进 Architecture 也不自动证明一条约束已被采纳。源码只能证明所读实现，不能单独证明实际运行经过该路径。实验只覆盖实际版本、配置和负载。产品要求需要确认来源，不能用一次测试决定是否保留。

摘要、合并和引用必须继承原结论的条件、未知部分与来源。多份转述同一个假设不构成多份独立证据。阅读或引用不是重新验证；仅复核某一结论时，只更新该结论的验证信息。

## 冲突：定位陈述后再修复

比较具体的冲突陈述与来源，先排除版本、范围和语义不同造成的表面矛盾，再核查证据和决策来源：

| 判定 | 动作 |
| --- | --- |
| 实现偏离仍有效的要求 | 在本次授权内修复实现，验证要求覆盖的行为 |
| 文档描述已过期 | 更新对应描述，保留必要的理由与证据边界 |
| 要求或决策已获授权改变 | 更新当前入口、受影响记录及本次范围内的实现 |
| 证据不足，暂不能判定 | 标明冲突、未知项和最小复核动作，不制造一致性 |

任何结论都可以挑战，但发现旧技术限制失效不等于有权取消兼容承诺或产品要求。依据已有授权继续能完成的修正；只有缺少的决定或证据确实阻塞任务时，才向相应决策者提出具体问题。不要让代码或文档自动获胜。

## 结束：只维护有剩余价值的知识

先问：丢失这条知识会影响未来的重要判断吗？能否低成本、可靠地从现有材料恢复？优先保存非显然理由、真实约束、已确认的困难根因，以及仍值得调查的重要假设。普通函数说明、完整聊天记录和无剩余价值的探索过程通常不需要沉淀。

先按上述发现入口确认沉淀授权；尚未授权的自主发现只提出建议。在本次文档维护授权内，选择最小动作：

- 已有记录覆盖：更新原处，避免再写一份同义结论。
- 新发现值得保留：在已有主题或合适的新文件中记录结论、理由、条件和证据线索。未验证的有用假设明确标注，不升级为根因。
- 前提变化：修订对应结论；不能核实时标明待复核，不因日期变新就声称有效。
- 内容重复或失效：合并或退出当前入口；涉及删除时按 [局部整理](references/maintenance.md) 区分退出、保留路标和物理删除。
- 没有新的长期价值：正常完成任务，无需创建文件或固定格式的维护报告。

让未来任务能找到新增或替代内容：更新相关入口或入链，用“什么任务需要读、读哪里、何时继续展开”组织路由，事实和理由留在正文。日常维护优先复用现有结构；发现结构妨碍检索或维护时，按 [整理与重建](references/maintenance.md) 主动提出重建建议，不把“复用”当作永久保留旧目录的要求，也不初始化六个空目录。

交付前核对本次结论是否超出证据、是否遗漏未知项、入口与链接是否仍可达。简短报告实质更新及仍影响任务的冲突，不宣称未检查的整库知识已刷新。
