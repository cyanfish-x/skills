# 记录与路由

需要沉淀新知识或建立任务入口时使用。以下是可裁剪的写法，不要求每条知识填写统一表格；没有依据的信息写明未知或省略，不补造版本、日期、来源和决策者。

## 一条可复用的结论

用一段话回答实际重要的问题：结论及性质、来源、适用范围、验证边界、重新评估条件；若有约束力，再指出确认来源。

以下均为虚构示例，不能作为目标项目的事实：

> **观察**：在依赖 2.4、单工作线程的复现实验中，关闭操作仍留下一个监听器。证据为项目保存的复现脚本及运行记录。尚未检查多线程路径。修改关闭流程或升级依赖后，需要重新运行复现；当前不据此断言所有资源泄漏都由该监听器导致。

真正落盘时提供可定位的路径、源码符号与版本、提交、实验产物或来源链接。引用应能让后续使用者复核；行号可以辅助定位，但不要只留容易漂移的行号。会话确认若没有持久链接，可记录确认日期、角色及确认内容，并诚实说明来源是本次会话。

> **假设**：请求重复可能来自重试层；当前只有时间相关性，未追踪调用来源。保留此线索是因为问题低频且复现成本高。下一次应关联请求标识与重试日志。转述本段时继续保留“可能”和未验证范围。

不要把“曾读过”“多人引用过”“文件日期很新”写成已验证；实际复核时记录检查的对象和结果。

## 自主发现的沉淀建议

在写入前，把有价值的候选整理成可直接审查的建议。例如以下虚构场景：

> 本次复现确认：依赖 2.4 的单工作线程关闭路径会留下一个监听器，证据是本次复现脚本和运行记录；多线程路径尚未验证。未来修改关闭流程时可能再次遇到，建议新建 `docs/engineering/listener-cleanup.md`，记录复现条件、根因和升级后的复核方式，并补充入口链接。是否按此内容沉淀？

实际建议用真实证据位置与目标路径替换示例。已有相同结论时建议修订原记录或改善入口，不新建重复文件。若仅有相关性，写成“尚未验证的假设”，不能使用示例中的“确认”和“根因”。

用户已经要求记录或授权持续维护时，直接完成这些动作，报告实际保存内容即可，不套用示例的确认问题。

## 当前决策

只保留仍影响选择的部分：

> 当前选择 A，采纳依据是已确认的需求或决策来源 S；原因是 X 和 Y。真正需要维持的是 Z。B 曾因 Q 被放弃；如果 X 或 Q 改变，应重新比较 A 与 B。现有证据只覆盖 C，D 尚未确认。

Agent 的推荐写成建议，不写成已采纳决策。替换当前选择时，让入口直接指向新状态。已有不可改写的 ADR 或审计记录可以继续保留，通过当前摘要和替代链接说明关系。

## 适配已有结构

| 用户需要回答的问题 | 可复用的语义位置 |
| --- | --- |
| 为什么做、范围与取舍 | Intent |
| 调用者应该看到什么行为 | Spec |
| 职责、所有权、生命周期与不变量 | Architecture |
| 为什么采纳、何时重评 | Decisions |
| 难以恢复的根因与工程陷阱 | Engineering |
| 外部证据及未确认部分 | Research |

一个主题文件可以用章节承载几种用途。为同一结论选一个维护位置，其他位置引用它。Research 中可以包含推测；其所在目录不赋予事实地位。

## 最小路由

入口示例，路径仅作示意，使用时替换成真实且已检查的目标：

| 当前任务 | 先读 | 继续展开的条件 |
| --- | --- | --- |
| 修改公开调用行为 | API 规范中的兼容章节 | 改变失败返回时，再读错误模型决策 |
| 改变关闭或释放流程 | 资源所有权章节 | 涉及后台工作线程时，再读关闭竞态经验 |
| 升级依赖 | 依赖相关决策与有版本前提的记录 | 实际触及旧缺陷路径时，再读复现实验 |

路由不抄写完整事实，不列出所有文档，也不要求一次读完一行的全部材料。单个记录已有清晰入口时，不必再造总索引。
