# 假设驱动调试方法论

调试最忌讳"随机改改看"（shotgun debugging）。结构化的做法是**假设驱动**：先提出有限个互斥猜想，用数据逐一验证。

## 第 1 步：把现象翻译成猜想

用户的描述往往是模糊的现象（"红线消失了""点了没反应""数据不对"）。你的任务是把它拆成**有限个互斥、可证伪**的猜想（通常 2~4 个）。

### 好猜想的标准

1. **可证伪**：能设计一个埋点，用日志数据明确判定"是"或"不是"。
2. **互斥或可区分**：不同猜想对应不同的日志特征，不会都指向同一组数据。
3. **覆盖主要可能性**：不要漏掉高频原因。

### 反例（坏猜想）

- ❌ "可能是 bug" —— 不可证伪，废话
- ❌ "代码哪里有问题" —— 太泛，无法埋点
- ❌ "也许是浏览器问题" —— 无法用代码埋点验证

### 正例（好猜想）

现象："拖动进度条，红线跑两轮后消失"

| 猜想 | 如果成立，日志特征 | 如果不成立，日志特征 |
|---|---|---|
| H1 DOM 被框架重渲染清除 | `document.contains(line)` 出现 `false` | 始终 `true` |
| H2 位置算错（visibleLeft 越界） | `visibleLeft` 为负或 > clientWidth | 始终在 `[0, clientWidth]` 内 |
| H3 滚动不同步（scrollLeft 设置未生效） | 设置后读回的 `actualScrollLeft` ≠ 目标值 | 两者相等 |

三组日志特征互不重叠，一次复现就能区分。

## 第 2 步：为每个猜想设计最小埋点

每个猜想 1 个 probe_id，采集**能区分该猜想的最小字段集**（见 `probe_patterns.md`）。

不要贪多。猜想是 H1/H2/H3 三个，就埋三个点。满屏埋点会让日志噪声淹没关键信号。

## 第 3 步：用日志数据判决

读日志后，逐条对照第 1 步的"日志特征表"：

```
H1: exists 全程 true → 证伪（DOM 没被清除）
H2: visibleLeft 始终在 [0,1613] 内 → 证伪（位置算对了）
H3: scrollLeft=2000 但 actualScrollLeft=0 → 证实（滚动没生效）✓
```

**让数据说话，不要靠猜。** 如果一个猜想被日志数据明确证实，就锁定它作为根因。

## 第 4 步：迭代

三种结果：
- **全部证伪**：当前猜想的范围错了。基于"排除了什么"重新提猜想。例如已知"DOM 没被清除、位置算对了"，那问题在"渲染/可见性"层面，往这个方向提新猜想。
- **部分证实但不够确定**：补一个更细的埋点缩小范围。
- **明确证实**：进入修复。

## 常见认知陷阱

| 陷阱 | 对策 |
|---|---|
| 只提一个猜想就动手改 | 强制提 2~4 个互斥猜想，即使你"觉得"就是某一个 |
| 猜想之间不互斥（都指向同一原因） | 检查每个猜想的日志特征是否真的不同 |
| 靠"经验"跳过验证直接修 | 哪怕 90% 确信，也用一次埋点确认，剩下 10% 常常是惊喜 |
| 采太多数据淹没信号 | 每猜想最小字段集；用 probe_id 分通道 |
| 改了多处再看效果 | 一次只验证一组猜想，避免"不知道是哪个改起作用" |

## 与通用调试的关系

本 skill 专注"前端 + 埋点取证"这一环。更通用的调试纪律（复现、最小化、定位根因而非症状、加回归测试）见 `debugging-and-error-recovery` skill，两者互补。
