# Living Context v2

> Knowledge Lifecycle for Human–Agent Collaboration
>
> 管理长期由人类与 AI Agent 共同开发的项目知识：让它产生、被验证、沉淀、被复用、保持相关，并在失去价值时退出。

**状态：讨论稿。** 本文是理念与原则的修订版，用于指导后续 skill 设计，不是已经启用的项目执行规范。原始纲领保留在 [design.md](design.md)；v1 与 v2 用于设计对照，不应作为两套并行生效的规则加载。正式采用时，应明确唯一的当前入口。

相对 v1，本版保留昂贵知识、最小充分上下文和完整生命周期，补充六项边界：可信度与约束力分离；验证范围与来源继承；重新判断的权限边界；退出与删除的区别；按事件局部维护；以未来任务表现衡量收益。

## 一、目标：让知识提高判断质量

> Knowledge should amplify intelligence, not constrain it.
>
> 知识应该放大智能，而不是束缚智能。

Living Context 管理项目知识的生命周期。文档只是载体，目标是让积累的知识持续提高未来开发者和 Agent 的判断质量，而不是增加他们识别过期结论、重复信息和隐含前提的负担。

它优先提供那些重新获得成本高、容易被误判、仍然影响当前决策，且无法通过短时间阅读代码可靠恢复的知识。使用者应当理解已有证据、真实约束和历史理由，再对当前问题独立判断。

知识可以承载必须遵守的产品要求、兼容承诺、安全边界和架构不变量。历史实现、临时方案、旧版本限制和 Agent 的个人偏好，不应被包装成永久规则。

Living Context 追求 **Minimum Sufficient Context：最小充分上下文**。充分意味着覆盖当前任务的关键行为、约束和风险；最小意味着不要求使用者为无关历史支付阅读成本。简短本身不是目标，不能为了缩短文本而丢失证据边界或关键理由。

## 二、保存什么：昂贵且仍有价值的知识

> Preserve expensive knowledge, not obvious information.

判断一条知识是否值得长期保存，先问：

> 一个能力很强、不了解项目历史的 Agent，能否低成本、可靠地重新获得它？失去它，会不会影响未来的重要判断？

难以恢复的产品意图、非显然的设计理由、经过艰难排查确认的根因、容易重犯的生命周期陷阱，通常值得保存。显而易见的函数行为、重复的目录介绍、已经失去作用的探索过程，通常不值得维护。

重建成本不是唯一条件。昂贵但已经与项目无关的研究，也可能退出；很短但影响兼容性的重要约束，仍应保留。

沉淀时保存结论、理由、适用条件和足够的证据线索，无需搬运整个聊天或调试过程。若某份实验产物是后续复核不可替代的证据，可以保留产物或可靠引用，而不是只留下无法核查的摘要。

## 三、可信度与约束力是两个维度

知识需要同时回答：**这条陈述有什么依据？它是否有权约束当前项目？** 两者不能混为一谈。

| 内容 | 证据或确认状态 | 对项目的作用 |
| --- | --- | --- |
| 某版本源码存在特定行为 | 在对应版本和路径下有源码依据 | 提供实现判断依据 |
| 用户确认旧 API 必须兼容 | 已确认的产品要求 | 在适用范围内必须遵守 |
| 实验中方案 B 比 A 更快 | 在该环境、负载和测量方法下成立 | 提供选择材料，不自动决定选型 |
| 项目已采纳方案 A | 有明确的决策来源 | 在适用范围内构成当前设计基线 |
| Agent 推测问题源于缓存 | 尚未检验的假设 | 指导调查，不能当作已确认根因 |

Fact、Observation、Inference 描述事实及认识状态；Constraint、Decision、Guidance 描述要求、选择或建议。Research 是知识用途与来源类别，其中仍可能混有事实、观察和推测，不能因被放进 research 就整体获得可信度。

可靠的外部事实不会自动成为项目要求；项目要求也不需要通过运行实验来证明其正当性，而需要明确的确认来源与适用范围。

## 四、验证必须有边界

重要知识应尽可能交代以下信息，而不是只有一个“已验证”标签：

- **性质与内容**：这是事实、观察、推测、要求、决策还是建议？具体声称什么？
- **来源与依据**：来自谁的确认、哪份文档、哪个源码版本或哪次实验？
- **适用范围**：涉及哪些模块、接口、环境、版本和运行条件？
- **验证边界**：实际确认了什么，还有什么没有确认？
- **约束来源**：如果它要求必须遵守，要求来自哪里，适用于谁？
- **重新评估条件**：哪些前提变化会影响它，届时如何复核？

这些是应能回答的问题，不是要求每条知识填写同样长的表格。

一个有边界的技术结论可以表述为：

> 在版本 V、条件 C 下，通过证据 E 确认结论 X；尚未确认 Y。当条件 C 或相关实现变化时，需要重新检查 X。

官方文档、源码、实验与运行观察不能组成固定的可信度阶梯。文档可能描述承诺，源码表明实现路径，实验表明特定条件下的结果；应选择能支持当前陈述的证据。阅读源码不自动证明实际运行走了该路径，局部实验也不自动证明所有环境都成立。

产品要求需要确认，技术假设需要检验，当前行为需要观察。**证据支持的范围必须覆盖结论声称的范围。**

### 防止不确定性在传播中消失

摘要、转述和合并必须继承原结论的适用条件与不确定性。若多篇文档源于同一条推测，它们仍然只有一个未经验证的来源。

阅读、引用和复用不算重新验证，不能因此刷新“最后验证”状态。只有重新核对相关证据后，才能更新对应结论的验证记录；检查了某一部分，也不能宣称整篇文档重新有效。

重要但未确认的假设可以暂时保留，前提是明确标注，并说明它为何值得继续调查。不能为了保存一个有用线索而把它升级成事实。

## 五、可以质疑，但改变约束需要相应权限

任何结论都可以在新证据、前提变化或目标调整后被重新评估。**能够提出挑战，不等于已经获得修改需求或取消约束的权限。**

Agent 可以指出兼容要求的成本、证明旧技术限制已失效、提出新的架构方案。在已有授权范围内，可以调整实现并验证必要的不变量；超出授权的产品要求、兼容承诺或其他已确认约束，应由相应决策者确认变更。

不需要因此给每次知识修订增加人工审批。纠正错误引用、补充证据、标记待复核状态等维护，应在已有授权内正常进行。需要区分的是“修正文档对现实的描述”与“改变项目应该遵守的要求”。

Architecture 描述当前期望的结构、职责、所有权、生命周期和不变量。更换实现方式时，应明确哪些约束仍须维持，而不是把当前结构当作永远不可改变的形式。

## 六、知识模型：语义先于目录

不同知识回答不同问题：

| 语义空间 | 主要问题 |
| --- | --- |
| Intent | 为什么做，目标、范围与取舍是什么？ |
| Spec | 用户、API 或调用方应该观察到什么行为？ |
| Architecture | 当前期望怎样组织职责、边界、所有权和生命周期？ |
| Decisions | 为什么采纳当前选择，何时应重新考虑？ |
| Engineering | 哪些难以重建的工程经验仍有复用价值？ |
| Research | 哪些外部技术证据可供决策参考，边界是什么？ |

这是一套语义模型，不要求初始化六个空目录，也不要求把同一问题拆成六篇文章。可以适配项目已有文档结构，通过章节或链接建立关系，避免重复陈述需要同步维护的同一结论。

代码是实现状态的直接证据；实际行为还可能取决于配置、环境和执行路径。代码不能独自证明产品应该如何表现。Research 提供材料，已采纳的 Decision 表达项目选择，二者不能互相替代。

### Living Decision

一个有长期价值的决策，应说明当前选择、理由、真实约束、重要替代方案，以及重新评估条件。例如：

> 当前选择 A，因为 X 和 Y。真正需要维持的是 Z。B 曾因 Q 被放弃；如果 X 或 Q 不再成立，应重新比较 A 与 B。

决策改变后，应让当前入口直接表达新状态，不要求使用者逐篇拼接历史 ADR。项目若已有审计或历史保留要求，可以保留原记录，并提供明确的当前摘要与替代关系。

## 七、生命周期：由事件触发，而非每次全量执行

> Discover → Verify → Distill → Route → Reuse → Refresh → Prune
>
> 产生 → 验证或确认 → 沉淀 → 路由 → 复用 → 更新 → 退出

这是知识可能经历的生命周期，不是每个开发任务必须执行七遍检查的清单。

| 阶段 | 核心判断 |
| --- | --- |
| Discover | 这是值得继续关注的候选知识吗？ |
| Verify | 它是什么性质，有什么证据或确认，边界在哪里？ |
| Distill | 哪些内容值得长期保存，如何保留必要理由？ |
| Route | 未来什么任务需要它，如何找到它？ |
| Reuse | 它与当前任务及环境是否匹配？ |
| Refresh | 哪些前提发生了变化，哪些结论需要修订？ |
| Prune | 它应继续活跃、合并、退出默认上下文，还是删除？ |

日常开发主要通过三个时机维护知识：

1. **开始任务**：查找相关知识，检查影响当前判断的关键前提。
2. **工作过程中**：遇到冲突或昂贵发现时，保留候选结论和必要证据。
3. **完成任务**：对本次触及的知识做必要的新增、修订、合并或移除，同时维护相关入口。

依赖升级、需求变化、模块重构和新运行证据，应触发对应范围的复核。全库整理可以作为独立任务，不应成为每次小修复的附加成本。

**“本次没有值得长期沉淀的新知识”是正常结果。** 维护成本本身必须计入 Living Context 的收益判断。

## 八、路由：从任务找到知识，并知道何时停止

> Load only relevant context.

`docs/index.md` 或项目已有入口应帮助使用者根据任务找到知识，而不只是列出所有文件。基本关系是：

> 任务或模块 → 相关知识 → 需要继续展开的条件。

例如，修改公开 API 时找到兼容约束；改变资源释放方式时找到生命周期说明；升级依赖时找到依赖旧版本行为的工程经验与决策。

入口应保持简短，只描述何时需要哪些内容。具体事实与理由放在对应知识中，避免索引演变成第二套完整文档。

当当前任务所需的行为、约束、职责边界和关键风险已经明确，且没有会改变当前决定的未解决冲突时，应停止扩展上下文。后续出现新的依赖或证据，再按需展开。找不到相关记录不代表没有约束，仍需进行必要的代码和需求调查。

## 九、冲突处理：先定位陈述，再判断如何修复

当 Code、Spec、Architecture、Decision 或 Research 相互不一致时，这是可能发生漂移的信号，也可能是版本、范围或语义不同造成的表面冲突。

处理顺序应是：

> 定位具体冲突 → 比较版本与适用条件 → 核查证据和决策来源 → 判断需要修复的对象 → 在权限范围内更新并验证。

不应自动让代码覆盖 Spec，也不应直接按文档修改实现。先区分实现偏离、文档过期、需求已变或证据不足。

尚不能判定时，应明确保留冲突和未知部分，继续不依赖该结论的工作；只有缺失的决定或证据确实阻塞当前任务时，才需要请求补充。不能为了让文档看起来一致而制造未经确认的结论。

Living Context 不保证所有知识永远正确，而要求错误或失效有机会被发现，并有清晰的修订路径。

## 十、退出：保留价值，而非保留全部历史

> Docs describe what still matters; Git preserves what happened.

知识的终点不一定是永久保存。**退出默认上下文，与物理删除是不同操作。**

| 情况 | 处理原则 |
| --- | --- |
| 重复、显然、无剩余价值 | 删除，或并入已有内容 |
| 已被新知识吸收 | 合并，保留必要理由并更新引用 |
| 已失效且会误导当前判断 | 从当前有效入口移除，纠正或明确替代 |
| 暂不适用，但有较高复发风险或重建成本 | 保留简短原因、适用提示或历史指针，按需发现 |
| 仍有审计、契约或明确历史保留要求 | 按要求保留，区分历史状态与当前规范 |

Git 保存历史，不自动解决历史的可发现性。若删除后未来只能通过大规模考古恢复重要理由，就应考虑保留一个简短路标，而不是留下整份探索报告。

长期未读取不能单独证明知识无价值；低频但代价高的陷阱仍可能值得保存。时间可以触发检查，不能独自决定结论已失效或应删除。

“自然消失”指知识在正常维护中根据价值退出，不意味着按年龄或访问次数无条件自动删除。删除或合并时应同步维护入口与引用，避免留下悬空路由。

## 十一、成功标准：改善后续任务，而非增加文档产量

Living Context 的核心假设是：保存与维护知识的成本，能够换来更少的重复调查、更少的误判，以及更可靠的后续变更。这个假设需要通过任务表现检验。

可以用以下场景验证：

- 新 Agent 能找到一个代码中不明显的真实约束，并正确应用。
- 依赖升级后，Agent 能识别旧版本限制需要复核，而非继续机械遵守。
- 代码与 Spec 冲突时，Agent 会调查来源和前提，而非改文档迎合代码。
- 推测经过多次摘要与复用后，仍保留不确定性，没有被重复引用升级为事实。
- 被替代方案的高价值失败原因仍可按需找到，同时不占用无关任务的默认上下文。
- 普通小修复可以结束于“无需新增知识”，不被迫生成文档。

评估时比较相近任务的调查成本、约束遗漏、错误复用、人工纠正和维护开销。文档数量、字段完整率、删除字数或加载文本量，都不能单独代表成功。

## 十二、落成 skill 的边界

本文定义理念和判断原则。后续 `SKILL.md` 应提供简短、可执行的触发条件、读取规则、维护动作和反例，目录与字段模板按需要展开。

第一版宜优先验证三个能力：相关知识检索、证据与约束区分、任务结束时的局部维护。暂不将复杂知识图谱、自动可信度评分、按时间自动删除或每次任务的全库巡检作为必要组成。

这套机制自身也应遵守最小充分上下文：规则应足够支持判断，维护负担应与知识价值相称。最终，一个初次进入项目的高能力 Agent 应能快速理解目标、行为、边界、关键理由和仍待确认的部分，把推理能力留给今天真正新的问题。
